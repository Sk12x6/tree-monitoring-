Step 0

WiFi & Telegram Alerts

This guide walks you through adding live Telegram alert messages to your ArborGuard v2.0 system. When the ESP32 detects tree cutting (or dry soil), it sends an instant alert to your Telegram phone — no SIM card, no GSM module, just the ESP32's built-in WiFi.

What you need

ItemStatusNotes
ESP32 + all sensorsAlready haveNo new hardware needed
2.4 GHz WiFi networkNeed accessESP32 does not support 5GHz
Telegram accountNeed accountFree, takes 2 minutes
Bot Token + Chat IDWill createSection 2 of this guide
💡
Simple version: Your ESP32 connects to your home WiFi. When something bad happens, it calls Telegram's API (like visiting a website) and sends you a message. That's the entire idea.
⚠
Technical note: The ESP32 uses WiFiClientSecure to make HTTPS POST requests to api.telegram.org/bot{TOKEN}/sendMessage. We skip certificate verification (setInsecure()) since rotating certs in embedded systems is messy — acceptable for a personal IoT node, but replace with setCACert() in a production deployment.

⚠
GPIO 34, 35 are input-only pins. They have no internal pull-up resistors. Use them only for ADC reads — never try to drive output on these pins. GPIO 32 is fine for both input and output.
ℹ
I2C shared bus: BH1750 (address 0x23) and SH1106 OLED (address 0x3C) both sit on the same two wires — GPIO 21 (SDA) and GPIO 22 (SCL). Each device has a unique address so they don't conflict. Just connect both devices' SDA to GPIO 21 and both SCL to GPIO 22.

// ================================================================
//  WIFI + TELEGRAM CREDENTIALS
//  !! Do NOT push this file to a public GitHub repo !!
// ================================================================
#define WIFI_SSID      "Your_WiFi_Name"
#define WIFI_PASSWORD  "Your_WiFi_Password"
#define BOT_TOKEN      "1234567890:ABCdefGHIjklMNOpqrsTUVwxyz"  // from BotFather
#define CHAT_ID        "987654321"                               // your Telegram numeric ID

// ================================================================
//  NETWORK STATE
// ================================================================
namespace Net {
  constexpr uint32_t RECONNECT_MS        = 30000;  // retry WiFi every 30s
  constexpr uint32_t CONNECT_TIMEOUT_MS   = 10000;  // 10s connection attempt
  constexpr uint32_t TELEGRAM_COOLDOWN_MS = 60000;  // max 1 message per minute
  uint32_t lastReconnect  = 0;
  uint32_t lastTgSent     = 0;
  bool     online         = false;
}

3c — WiFi manager function

This is mostly non-blocking — it only stalls during the initial connection attempt (max 10 seconds) then retries in the background. The system keeps reading sensors normally while WiFi reconnects.

New function — add before setup() 
// ================================================================
//  WIFI MANAGER (mostly non-blocking)
// ================================================================
void wifiTask(uint32_t now) {
  if (WiFi.status() == WL_CONNECTED) {
    Net::online = true;
    return;
  }

  Net::online = false;

  if ((now - Net::lastReconnect) < Net::RECONNECT_MS) return;
  Net::lastReconnect = now;

  Serial.print("[WiFi] Connecting to ");
  Serial.println(WIFI_SSID);

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);

  uint32_t t = millis();
  while (WiFi.status() != WL_CONNECTED && (millis() - t) < Net::CONNECT_TIMEOUT_MS) {
    delay(300);
    Serial.print(".");
  }
  Serial.println();

  if (WiFi.status() == WL_CONNECTED) {
    Net::online = true;
    Serial.println("[WiFi] Online — IP: " + WiFi.localIP().toString());
  } else {
    Serial.println("[WiFi] Failed — retrying in 30s");
  }
}

3d — Telegram send function

This sends one HTTPS POST to Telegram. It takes 200–800ms to complete due to TLS handshake, so it is wrapped by a rate limiter to prevent blocking the main loop repeatedly.

New functions — add after wifiTask() 
// ================================================================
//  TELEGRAM SENDER
// ================================================================
bool sendTelegram(const String& msg) {
  if (!Net::online) {
    Serial.println("[Telegram] Skipped — no WiFi");
    return false;
  }

  WiFiClientSecure client;
  client.setInsecure();    // skips SSL cert check — fine for personal IoT use
  client.setTimeout(5);

  HTTPClient http;
  String url = "https://api.telegram.org/bot";
  url += BOT_TOKEN;
  url += "/sendMessage";

  http.begin(client, url);
  http.addHeader("Content-Type", "application/json");
  http.setTimeout(6000);

  String body = "{\"chat_id\":\"";
  body += CHAT_ID;
  body += "\",\"text\":\"";
  body += msg;
  body += "\",\"parse_mode\":\"Markdown\"}";

  int code = http.POST(body);
  http.end();

  if (code == 200) {
    Serial.println("[Telegram] Message sent ✓");
    return true;
  }
  Serial.printf("[Telegram] Error HTTP %d\n", code);
  return false;
}

// Rate-limited wrapper — call this from alert logic, not sendTelegram() directly
void sendAlertTelegram(const String& msg, uint32_t now) {
  if ((now - Net::lastTgSent) < Net::TELEGRAM_COOLDOWN_MS) {
    Serial.println("[Telegram] Rate limited — skipping");
    return;
  }
  if (sendTelegram(msg)) {
    Net::lastTgSent = now;
  }
}

Step 4

Testing & Debugging

Before deploying to a tree, verify each layer independently.

Layer 1 — WiFi connects

Upload the code and open Serial Monitor at 115200 baud. You should see:

Expected Serial output on boot
[WiFi] Connecting to Your_WiFi_Name
[WiFi] ......
[WiFi] Online — IP: 192.168.1.105

If it says Failed — retrying in 30s, double-check your SSID and password. The ESP32 can only connect to 2.4 GHz networks — make sure your phone hotspot or router is on 2.4 GHz, not 5 GHz only.

Layer 2 — Manual Telegram test

Add a temporary test call in setup() to verify the bot works before the sensors need to trigger it:

Temporary test in setup() — remove after confirming 
// Add at the end of setup() — remove after test passes
delay(3000); // wait for WiFi to settle after boot
sendTelegram("*ArborGuard v2.0 Online*\nBoot successful. Node ready.");

If you receive this message on Telegram, the entire stack — WiFi, HTTPS, bot token, chat ID — is working. Remove this test line before final deployment.

To manually simulate a tree-cutting event without smashing your sensor, temporarily lower the thresholds in the code for testing:

Common issues

SymptomLikely causeFix
WiFi connects but no Telegram message Haven't started chat with bot Search your bot on Telegram, press Start
HTTP Error 401 Wrong Bot Token Re-copy token from BotFather — no spaces or line breaks
HTTP Error 400 Wrong Chat ID or JSON formatting error Verify Chat ID via @userinfobot, check for quotes around it in code
WiFi stuck at "......" forever Wrong SSID / 5 GHz network Confirm network is 2.4 GHz; check SSID exact spelling (case-sensitive)
Alert triggers then never again TELEGRAM_COOLDOWN_MS (60s) still active Normal behavior — wait 60s, or lower the cooldown for testing
System slows down when sending TLS handshake blocks loop for ~500ms Expected — WiFiClientSecure is inherently blocking. For strict real-time, offload to FreeRTOS task on Core 0.
